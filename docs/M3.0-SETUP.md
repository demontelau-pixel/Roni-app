# RONI M3.0 — Wallet infrastructure setup

This is infrastructure only. Nothing in the app's UI changes yet — the
`/wallet` route still shows its M1 placeholder until a later milestone
wires a real screen up to what's described here. No real credentials
appear anywhere in this document or in the repo.

## 1. Environment variables

Both are already set locally per your message — nothing to create.
What you need to **confirm**:

| Variable | Where it's read | Safe to expose to the browser? |
|---|---|---|
| `NEXT_PUBLIC_SUPABASE_URL` | `lib/supabase/client.ts`, `lib/supabase/server.ts`, `middleware.ts` | Yes — it's just your project's URL |
| `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` | same three files | Yes — Supabase's current low-privilege key; Row Level Security decides what it can reach |

M3.0 deliberately introduces **no** service-role/secret key. If a
future milestone genuinely needs one (e.g. a server-side job that must
bypass RLS), that's a deliberate, separate decision to make then — not
something this patch does implicitly.

**Before this reaches production:** confirm both variables are set in
Vercel for **both Production and Preview** environments (Settings →
Environment Variables). `src/middleware.ts` checks for them and skips
Supabase entirely if they're missing — it will not crash the site —
but Wallet-related features obviously won't work until they're set
there too.

## 2. Applying the SQL migrations

Three files, in `supabase/migrations/`, **apply them in order**:

1. `0001_core_tables.sql` — profiles, households, household_members, policies
2. `0002_policy_documents_and_extraction.sql` — documents, extracted data, evidence
3. `0003_storage.sql` — the private Storage bucket + its access policies

**Option A — Supabase Dashboard (simplest):**
Project → SQL Editor → paste the contents of `0001...sql` → Run. Repeat
for `0002` and `0003`.

**Option B — Supabase CLI**, if you have it linked to this project:
```bash
supabase db push
```

Every statement is written to be safe to run more than once
(`if not exists`, `drop policy if exists` before `create policy`,
etc.) — re-running a file you've already applied won't error or lose
data. **Nothing here is destructive**: there is no `DROP TABLE`
anywhere in this milestone.

## 3. Storage — what the migration does vs. what to check by hand

`0003_storage.sql` creates the bucket via SQL (`insert into
storage.buckets ...`), so you don't need to click through the
Dashboard — but it's worth opening **Storage** in the Dashboard
afterward and confirming:

- A bucket named **`policy-documents`** exists.
- Its **Public** toggle is **off**. (The migration sets this
  explicitly and re-asserts it even if the bucket already existed —
  but a second pair of eyes on a private-documents bucket is cheap
  insurance.)

**Path convention every future uploader must follow** (documented at
the top of `0003_storage.sql` too):

```
{auth.uid()}/{policy_id}/{document_id}/{filename}
```

The Storage RLS policies trust only the first path segment (must equal
the uploader's own user id) — a user can never read, list, or write
into another user's folder, full stop.

## 4. Row Level Security — what's actually enforced right now

**Every table has RLS enabled**, and every policy is owner-based —
nothing uses `USING (true)` or any other broad grant. Concretely:

| Table | Who can read | Who can write |
|---|---|---|
| `profiles` | the row's own user | nobody directly (a trigger creates it on signup); user can update their own |
| `households` | the creator only | only the creator |
| `household_members` | the household's creator only | only the household's creator |
| `policies` | the owner (`owner_user_id`) only | the owner only |
| `policy_documents` | the owner only | the owner only |
| `policy_extracted_data` | the owner only | the owner only |
| `policy_extracted_data_evidence` | the owner only | the owner only |
| Storage `policy-documents` bucket | the uploader (by folder) only | the uploader (by folder) only |

**Household sharing is not implemented at all in M3.0** — only a
household's creator can see or manage that household, its members, or
any policy/document/extracted data tied to it. This was simplified
during review to remove a circular RLS dependency: an earlier draft
had `households`' policy querying `household_members`, and
`household_members`' policies querying `households` right back —
evaluating either table could re-trigger the other's RLS indefinitely.
The fix is one-directional: `household_members` still checks
`households.created_by`, but `households` no longer references
`household_members` at all. `0001_core_tables.sql` has two
commented-out extension points for real sharing later, each with a
note on what to design first (and how to avoid reintroducing the
circular dependency) before enabling either.

## 5. Supabase client architecture

Two client factories, matching Supabase's current recommended
`@supabase/ssr` pattern:

- **`lib/supabase/client.ts`** — for Client Components (the browser).
  Call `createClient()` inside a component; cheap to call more than
  once.
- **`lib/supabase/server.ts`** — for Server Components, Server
  Actions, and Route Handlers. `await createClient()` — it's async
  because it reads Next.js's cookie store per-request. **Never** make
  this a module-level singleton; each request needs its own instance
  bound to that request's cookies.
- **`middleware.ts`** — refreshes the session cookie on (almost)
  every request, per Supabase's own recommended pattern. It does
  **not** check who's signed in and **never redirects** — Marketplace,
  Home, Ask Roni, and everything else stay exactly as open as they are
  today. It explicitly skips `/api/*` (RONI's CMS routes don't need
  it) and Next's static asset paths.
- **`lib/auth/session.ts`** — `getUser()` and `requireUser()`, for a
  *future* protected `/wallet` to call. Nothing calls these yet.

## 6. Wallet service layer

`lib/wallet/repository.ts` is the only file that runs Supabase queries
against the Wallet tables. It takes a Supabase client as an explicit
argument (never imports one at module scope, for the request-scoping
reason above) and exposes: `getPolicies`, `getPolicy`, `createPolicy`,
`updatePolicy`, `createPolicyDocument`, `saveExtractedPolicyData`,
`getLatestExtractedPolicyData`. Every write determines `owner_user_id`
from the authenticated session itself — it's never accepted as caller
input, so there's no way to (even accidentally) write a row under
someone else's id.

## 7. What M3.0 implements

- Supabase client/server/middleware plumbing.
- 7 tables, fully normalized where it matters, JSONB where flexibility
  matters more (extracted data).
- RLS on every table and on Storage, owner-based, documented.
- A private Storage bucket with a secure, per-user path convention.
- TypeScript types for the database, the Wallet domain, and a first
  normalized Auto policy schema (`auto.v1`) with an explicit
  false-vs-unknown convention throughout.
- An evidence/provenance model so a future fact can always cite a
  document, page, and confidence.
- A real (not fake/mocked) service layer, unused by any UI yet.
- Masking helpers for policy numbers and VINs.

## 8. What's intentionally deferred to M3.1+

- Any Wallet UI screen (upload, list, detail) — `/wallet` keeps
  showing its current M1 placeholder.
- Actually protecting `/wallet` with `requireUser()` — the helper
  exists; nothing calls it.
- Sign-in/sign-up pages.
- AI extraction of any kind (OpenAI, Anthropic, or otherwise).
- Policy Q&A / Ask Roni reading real documents.
- Wallet → Marketplace comparison.
- Household sharing beyond "a member can see the household exists."
- Regenerating `lib/supabase/database.types.ts` from the real, applied
  schema via `supabase gen types typescript` (it's hand-written today,
  kept in sync with the SQL by hand — see the note at the top of that
  file).
